# M3.7 Metadata Enrichment and Operator Resolution Contract

**Status: local-only, disabled, and non-operational.** M3.7 defines a
station-scoped, provider-neutral metadata-candidate and operator-resolution
contract. It does not call MusicBrainz or another provider, read media tags,
access a filesystem, start a worker, activate persistence, or publish stream
metadata.

Only an M3.4-approved opaque processing job with an approved same-station asset
revision and valid source reference may form an enrichment request. Requests
contain opaque IDs, a bounded retry count, `metadata-fixture-v1`, provider
category/version, and analysis-version identifiers. They cannot carry titles,
artists, albums, filenames, paths, URLs, tags, media, provider payloads,
credentials, tokens, CSRF values, or raw SQL.

The disabled boundary supports `deterministic_fixture` and the future-compatible
`musicbrainz_compatible` category. The latter is explicitly unavailable and
never queried. A fixture preview creates one immutable, content-free candidate
with an opaque provenance reference and bounded confidence/category. It is
marked `enrichmentPerformed: false` and `deterministic_fixture`; it is not a
claim of metadata extraction or enrichment.

Candidate, outcome, resolution, retry, and evidence records use `id +
station_id`. Scoped reads return `not_found`; internal cross-station references
return `station_reference_forbidden`. Request and resolution idempotency is
deterministic. Candidate resolution is a separate, CSRF-protected operator
record with only `approved`, `rejected`, or `superseded` state. It neither
changes the immutable candidate nor updates an asset revision, prior analysis
result, programming state, schedule, runtime state, or stream metadata.

Failure, quarantine, and retry categories are bounded. A retry record is only
an append-only, explicit future authorization and never dispatches enrichment.
Candidates, outcomes, resolutions, and evidence are immutable local intent;
they cannot overwrite provenance, a normalization/cue recommendation, another
candidate, or an approved revision. Evidence contains only action, opaque
entity ID, station ID, profile/provider category, bounded state/category/count,
and UTC timing.

The API exposes read-only disabled status and safe candidate visibility, plus a
CSRF-protected explicit resolution record when a deterministic boundary is
injected for local tests. The default server boundary is empty and disabled.
There is no upload, lookup-now, enrich-now, provider call, worker, filesystem,
network, schedule, runtime, encoder, relay, Icecast, dynamic-metadata, or
listener-facing control. The UI exposes an accessible disabled status only.

M3.7 remains exclusively in the Programming Control Plane. PostgreSQL remains
the sole future live store; no SQLite, SAM, PAL, SHOUTcast, migration, staging
activation, or operational metadata propagation was introduced. M4 publication,
M5 runtime behavior, M7 encoding, and listener-facing metadata remain separate
future authority boundaries.

The next permissible item is separately approved **M3.8 — operator preview,
review, and authorization behavior**. Worker/persistence activation, provider
integration, staging rehearsal, schedule publication, runtime use, or metadata
propagation each require a separate explicit approval and content-free evidence.
