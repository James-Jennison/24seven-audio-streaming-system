# M2.4 Staging Backup, Restore, and DR Rehearsal Plan

## Status, scope, and authority

**Status: drafted locally for review.** This plan defines a future,
staging-only backup/restore and disaster-recovery rehearsal. It authorizes no
database connection, backup, restore, snapshot, volume operation, migration,
Compose invocation, service start, staging access, or deployment.

M2.4 applies only to the approved non-public staging boundary and a separately
approved, isolated non-production recovery target. It excludes production,
legacy infrastructure, media, scheduling, playout, DSP, automation, source
encoding, relays, Icecast, SHOUTcast, and listener-facing operations.

PostgreSQL remains the only live persistence direction; SQLite and `m1-store`
remain test-only. The programming control plane, playout runtime, source
encoder layer, and listener-facing Icecast layer remain separately deployable
and decoupled. Neither a backup nor a restore grants a control-plane action any
audio, encoder, relay, or stream authority.

## Required sequence and independent approvals

The following are distinct gates. None is implied by success at an earlier
gate:

1. **M2.2 migration-execution approval:** permits only the reviewed staging
   migration procedure after its documented prerequisites are satisfied.
2. **M2.3 topology-validation approval:** permits only approved non-public
   topology observation and application-boundary validation.
3. **M2.4 backup creation/verification approval:** permits creation and
   verification of an approved staging recovery artifact; it does not permit a
   restore.
4. **M2.4 restore-rehearsal approval:** permits restoration only into the named
   isolated recovery target and the approved validation steps; it never permits
   overwriting production.
5. **M2 completion acceptance:** requires owner review of bounded migration,
   topology, backup/restore, RPO/RTO, and unresolved-risk evidence. It does not
   authorize M3 or later work.

M2.2/M2.3 planning documents are accepted, but no migration execution or
topology validation has occurred. Their future evidence is a prerequisite for
the M2.4 operational gates.

## Recovery scope and artifact categories

The rehearsal scope is the PostgreSQL database schema and data created by the
reviewed staging migration, including the migration ledger and the five stable
station records. It is not a recovery of host configuration, credentials,
secret material, media, external services, or audio/listener state.

| Artifact category                  | Future purpose                                                                                                            | Boundary                                                                                       |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Approved Git/build artifact        | Identifies the application and migration contract being recovered                                                         | Immutable review reference; no executable change is implied                                    |
| Database backup artifact           | Source for an approved logical recovery or other owner-approved database recovery method                                  | Protected, non-public, and referenced only by opaque external identifier                       |
| Backup integrity manifest          | Records safe completeness/integrity result, creation time, scope classification, retention decision, and operator outcome | Contains no database content, object dumps, paths, keys, or credentials                        |
| Migration/seed verification record | Confirms expected migration-ledger and five-station facts after recovery                                                  | Safe pass/fail and expected-count/set result only                                              |
| Role/grant ownership record        | Confirms recovery identities and recovered runtime boundary remain least-privilege                                        | No role membership dump, raw grant statement, or secret material                               |
| Volume/snapshot boundary record    | If storage-layer recovery is selected, records ownership, lifecycle, source/target isolation, and safe outcome            | Does not expose volume IDs, paths, provider details, or snapshot locations                     |
| Recovery evidence record           | Captures RPO/RTO measurements, validation results, residual risks, and owner decision                                     | Content-free; no SQL, rows, programming payloads, filenames, or private infrastructure details |

The owner must choose and approve the recovery method before rehearsal. A
logical backup/restore and a storage-level volume/database restore are distinct
methods with different consistency, role, retention, and rollback behavior.
This plan does not select one by default.

## Authority matrix

| Authority class                   | Future M2.4 responsibility                                                                                   | Explicitly prohibited                                                                         |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| Owner/recovery decision authority | Approves method, target, destructive boundary, RPO/RTO acceptance, evidence location, and go/no-go decisions | Delegating an unapproved destructive restore or treating a plan as execution approval         |
| Platform/provisioning authority   | Provides the approved non-public source/recovery boundary and storage/volume controls                        | Runtime/UI use, ordinary programming, or implicit production access                           |
| Migration authority               | Supplies migration/ledger context only when separately approved                                              | Backup, restore, runtime, or role changes outside its approved migration scope                |
| Runtime authority                 | Is excluded from backup/restore creation; later validates only approved application data boundary            | DDL, schema ownership, backup/restore, role/extension management, or audio/listener control   |
| Backup authority                  | Creates and verifies the approved staging artifact under a backup-only approval                              | Runtime/UI, migration, production, or restore-target use                                      |
| Restore authority                 | Restores only to the named isolated recovery target under a restore-only approval                            | Source overwrite, production restore, routine runtime use, or unapproved privilege changes    |
| Evidence reviewer                 | Reviews content-free results and escalates failures                                                          | Accessing secrets, raw database content, or private topology details through project evidence |

No shared privileged identity is allowed. Backup and restore access use separate
opaque secret-reference categories and must not be reused for migration,
runtime, platform, or evidence access. No secret value, DSN, key, path,
repository identifier, or credential is documented or emitted.

## RPO/RTO definitions and acceptance targets

The proposed targets require explicit owner acceptance or revision before any
rehearsal:

- **RPO target: 24 hours.** Measure the elapsed time from the recovery-point
  timestamp of the most recent verified, in-scope staging backup artifact to
  the declared recovery incident/reference time. The evidence records only the
  measured duration and pass/fail result, not artifact location or contents.
- **RTO target: 4 hours.** Measure from the owner-authorized recovery start to
  completion of the approved restore, integrity validation, stable-station and
  role-boundary checks, and declared application-ready non-public recovery
  state. It excludes approval wait time and intentionally excludes any public
  listener, audio, or production validation.

The rehearsal must record measured RPO/RTO durations, target comparison,
measurement start/end definitions, failure class if missed, and owner decision.
Targets are planning objectives, not guarantees or service-level commitments.

## Preconditions and destructive-action safeguards

Before a future backup or restore action, all conditions below must be affirmed
in an owner-approved run record:

1. M2.2 migration execution and M2.3 topology validation have separately
   passed, or the owner has explicitly approved a bounded alternative rehearsal
   scope with its limitations.
2. The source is confirmed as staging and the recovery target is confirmed as
   isolated, non-public, and non-production.
3. The exact recovery method, backup scope, retention policy, integrity method,
   recovery target, approved operator, recovery decision owner, and safe
   evidence location are named outside this repository.
4. The owner has accepted or revised the 24-hour RPO and four-hour RTO targets.
5. Backup, restore, platform, migration, and runtime authorities are separate;
   the reviewed role/grant and `pgcrypto` authority artifacts exist.
6. A content-free verification probe exists for migration ledger/schema facts,
   stable stations, role separation, station isolation, and recovery readiness.
7. A restore can be performed without overwriting the staging source, any
   production target, or an unverified recovery boundary.
8. No application, Compose, audio/runtime, encoder, relay, Icecast, or
   listener process will be started except where a separate named gate permits
   the narrow recovery-readiness check.

Any failed or unknown item is a stop condition. The operator must not create an
ad hoc backup, retry a restore, overwrite a target, change grants, or expand
network exposure to make the rehearsal proceed.

## Future backup procedure — not authorized by this task

This procedure may be used only under a separate **M2.4 backup
creation/verification approval**:

1. Confirm the approved Git/migration artifact, staging-only source
   classification, backup method, operator, retention decision, and evidence
   location.
2. Confirm the backup authority is separate from migration, runtime, and
   restore authority; inject only its approved opaque secret reference.
3. Confirm a non-destructive, method-appropriate consistency boundary and
   record the recovery-point timestamp without recording database content or
   connection details.
4. Create the approved backup artifact. Do not include unapproved host,
   credential, media, or listener data.
5. Run the approved integrity/completeness verification for that method. Do not
   claim recoverability solely from artifact creation.
6. Record content-free artifact classification, scope, integrity result,
   recovery-point timestamp, retention outcome, and any exception.
7. Close purpose-bound access and stop. Do not restore, start an application,
   or treat backup verification as M2 completion.

## Future restore rehearsal procedure — not authorized by this task

This procedure may be used only under a separate **M2.4 restore-rehearsal
approval** after a verified approved backup exists:

1. Confirm the selected backup artifact passed integrity verification and is
   within the owner-accepted RPO target.
2. Confirm the named recovery target is isolated, non-public, non-production,
   and distinct from the staging source. If it is not, stop before any restore.
3. Confirm platform, restore, and evidence authorities are separate; inject
   only the restore authority's opaque secret reference.
4. Start the RTO measurement at the owner-authorized recovery start. Restore
   only the approved database scope using the owner-approved recovery method.
5. Validate the recovered boundary using approved content-free probes; do not
   use raw SQL dumps, row exports, or manual programming data edits.
6. Confirm the RTO measurement only after all required recovery validation
   checks pass. Close restoration access and retain no credentials or data in
   project evidence.
7. Stop at the owner decision point: accept rehearsal evidence, approve a
   bounded correction, or escalate to recovery review. Do not redirect runtime,
   application traffic, media, encoder, relay, or listeners to the target.

| Validation area            | Required future safe evidence                                                                                                         | Failure treatment                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Backup integrity/retention | Approved method reports a complete, in-scope, retained recovery artifact; safe timestamp and integrity outcome recorded               | Do not restore; owner chooses a new approved backup run or defers rehearsal                    |
| Migration ledger/schema    | Expected reviewed migration fact and schema/extension readiness verified without raw SQL/object dump                                  | Stop; compare with recovery method and escalate to migration/recovery decision owner           |
| Stable stations            | Exactly five expected stable station identities verified as a safe count/set result                                                   | Stop; no manual seed edits or repeated restore without approval                                |
| Station isolation          | Existing local test artifact plus approved recovery probe preserves `id + station_id`, `not_found`, and `station_reference_forbidden` | Hold recovery acceptance; investigate through approved non-content evidence                    |
| Role separation            | Recovery boundary confirms runtime remains non-DDL and authorities remain separate                                                    | Stop; correct only through a separately approved grants/ownership action                       |
| Application compatibility  | Local `npm run check` is green; any live control-plane connection/start is separately scoped and loopback-only                        | Do not claim application readiness from backup alone or start the application without approval |
| Volume/database lifecycle  | Chosen logical or volume method confirms source/target separation, ownership, and no source overwrite                                 | Stop and escalate; do not substitute a destructive method                                      |
| Safe failure behavior      | Failure closes purpose-bound access and records only class, UTC time, safe outcome, and decision reference                            | No automatic retry, rollback, or destructive cleanup                                           |
| Evidence/audit safety      | Review confirms no credentials, keys, DSNs, locations, SQL, rows, programming content, media, or private host data                    | Stop; follow separately approved incident handling before continuation                         |

## Rollback versus recovery decision tree

```text
Migration transaction failure
  → Use the M2.2 transaction/ledger decision process. This is not a DR restore.

Backup creation or verification failure
  → Do not restore. Preserve only safe failure evidence and obtain owner review.

Verified backup + isolated recovery target
  → Owner selects the approved method: logical recovery OR volume/database
    restore. Do not combine methods or overwrite a source by default.

Logical recovery failure
  → Stop; preserve the isolated target for approved diagnosis if safe. Do not
    switch to storage/volume recovery without a separate owner decision.

Volume/database restore failure
  → Stop; do not attach, replace, or overwrite another volume/target
    automatically. Escalate to platform and recovery decision authorities.

Recovered validation failure
  → Recovered data may exist but is not accepted. Hold the target isolated;
    owner chooses an approved correction, another bounded rehearsal, or deferral.

Any uncertainty about source, target, integrity, privilege, or exposure
  → Stop before destructive action and escalate.
```

Transaction rollback protects only the relevant migration transaction; it is not
a substitute for backup integrity, logical recovery, or volume/database restore.
No recovery method is assumed safe by default.

## Volume and Compose relationship

The current Compose definition names a Docker-managed PostgreSQL volume and
uses a loopback-only database binding. M2.4 does not invoke Compose or operate
the volume. Before a rehearsal, the owner must approve:

- whether the selected recovery method is logical, storage-level, or another
  bounded PostgreSQL method;
- volume/source/recovery-target ownership, lifecycle, capacity, and isolation;
- image/version and transport compatibility between source and recovery target;
- the interaction of the current `restart: unless-stopped` policy with backup,
  restore, and failure observation; and
- the M2.3-confirmed non-public topology boundary.

Backup/recovery does not authorize Compose topology changes, public exposure,
or a control-plane/runtime startup.

## Unresolved decisions and blockers

The following prevent safe approval of a future backup or restore rehearsal:

1. Owner choice of recovery method, backup tool/format, integrity method,
   retention, and protected artifact handling.
2. Owner-approved isolated recovery target and destructive-action boundary.
3. Accepted or revised 24-hour RPO and four-hour RTO planning targets.
4. Completed M2.2 migration execution and M2.3 topology-validation evidence,
   or an explicitly approved limited alternative scope.
5. Reviewed least-privilege role/grant/ownership artifact and `pgcrypto`
   installation authority.
6. Approved content-free probes for ledger/schema, stable stations, station
   isolation, role separation, application boundary, and artifact integrity.
7. Image/version/transport policy, volume lifecycle/ownership, capacity, and
   restart-behavior decision.
8. Approved evidence retention/access policy that does not expose backup
   repositories, secret references, database contents, or private topology.
9. Separately reviewed corrections to outdated README and historical
   architecture wording before those documents are used as an operator runbook.
