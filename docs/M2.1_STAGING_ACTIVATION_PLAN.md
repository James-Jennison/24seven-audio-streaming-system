# M2.1 Staging Activation and Migration-Rehearsal Plan

## Status and authority

This is the approved **M2.1 planning artifact**. It defines reviewable gates
for the first staging activation only. It authorizes no connection, migration,
Compose invocation, service start, backup, restore, VM access, deployment, or
runtime action. M2.2, M2.3, and M2.4 each require their own explicit approval.

The authoritative milestone boundaries remain:

```text
Proposed / Preview → Approved → Published (Versioned) → Executed (Runtime)
```

M2 activates persistence evidence only; it neither adds nor authorizes a
programming state transition, media action, playout action, encoder, relay,
Icecast, or listener-facing capability.

## Staging boundary

| Environment                  | Permitted purpose                                                                                          | Explicitly not equivalent to                                               |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Local workstation            | Static checks, unit/API/UI tests, and planning artifacts using injected fakes                              | An applied PostgreSQL database, a staging service, or operational evidence |
| Approved staging environment | Non-public PostgreSQL migration, application-boundary, topology, and recovery validation after named gates | Production, a public service, or a listener/runtime environment            |
| Production                   | Not in M2 scope                                                                                            | Staging or a rehearsal target                                              |

The planned staging target is the approved development environment
`24seven-audio-dev`, used only after an explicit M2.2 operational approval.
It remains SSH-administered and non-public. This plan does not connect to it or
record its address, keys, fingerprints, credentials, filesystem paths, or
provider details.

## Prerequisites and human gates

Before **any** future staging connection or mutation, the owner must approve a
named M2.2 run plan that identifies the staging target, approved maintenance
window, responsible operator, rollback decision owner, and evidence location.
The operator must confirm, without placing sensitive values in the repository:

- the target is the isolated staging database and is not production;
- a current, tested secret reference exists for each required identity;
- the required PostgreSQL version and the `pgcrypto` extension policy are
  compatible with `002_m1_control_plane.sql`;
- a verified pre-change recovery point exists before any state change;
- no public port, listener application, media, runtime, encoder, relay, or
  stream capability will be started; and
- the approved migration artifact matches the reviewed Git commit.

Any missing prerequisite stops the run. It is not replaced with a guessed
credential, elevated runtime role, alternate host, or unreviewed migration.

## Identity, role, and secret-reference contract

The eventual staging database uses separately managed identities. Names below
are responsibilities, not actual account names:

| Responsibility                      | Required authority                                                                                         | Prohibited authority                                                                                                |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Platform/provisioning administrator | Create the staging database, controlled extensions, and database roles during an explicitly approved setup | Application runtime, ordinary programming, or routine migration use                                                 |
| Migration authority                 | Apply the reviewed migration ledger and schema/seed changes during an approved M2.2 run                    | Runtime startup, operator UI use, or long-lived application traffic                                                 |
| Runtime authority                   | Connect only to the approved staging database and perform required application data operations             | `CREATE`, `ALTER`, `DROP`, extension management, migration-ledger writes, role management, or cross-database access |
| Backup authority                    | Create approved backup artifacts and read the minimum data required for recovery evidence                  | Runtime/application use, schema changes, or role management                                                         |
| Restore authority                   | Restore only into an explicitly approved isolated recovery target                                          | Production restore, routine runtime use, or role management beyond the approved restore procedure                   |

Before M2.2, the owner/operator must approve the exact least-privilege grants
and the extension-installation responsibility. The current migration requests
`pgcrypto`; if the migration authority cannot safely install it, the separate
pre-provisioning action must be designed and explicitly approved rather than
granting the runtime extra authority.

Configuration may carry opaque secret references only, such as the existing
runtime and migrator configuration variable names. It must never contain actual
connection URLs, passwords, certificates, tokens, or secret-manager locations.
Secret material is injected only into the approved process environment at run
time, never copied into repository files, documentation examples, tests, logs,
or captured command output. Rotation, revocation, and recovery must support:

1. creating a replacement reference without exposing either value;
2. validating the replacement in a separately approved, non-public run;
3. revoking the superseded reference and active sessions/connections; and
4. recording only the action, identity class, timestamp, safe outcome, and
   incident/reference identifier in an access-controlled record.

## Migration-rehearsal protocol

### Scope and artifact

The first approved staging migration targets only the isolated staging
database. The reviewed runner currently applies
`002_m1_control_plane.sql` through `DATABASE_MIGRATOR_URL`, records it in the
`schema_migrations` ledger, and then idempotently seeds the five stable station
definitions. `001_initial_stations.sql` is a historical M0 asset and is not in
the current PostgreSQL runner sequence. No production library or other source
is read, copied, or imported.

### Required preflight

The M2.2 operator records only safe pass/fail evidence that:

1. the reviewed commit, migration filename, and expected ordering match the
   approved run plan;
2. the target classification is staging and the migration authority is
   separate from the runtime authority;
3. the migration ledger state is understood and has no unapproved entries;
4. a pre-change backup/recovery point is available and its integrity status is
   known;
5. the extension policy, storage capacity, clock/UTC handling, and connectivity
   prerequisites pass; and
6. the Compose plan remains loopback-only and no application/runtime service
   will be started.

No command output containing connection strings, database names, host details,
raw SQL, row contents, or role membership is retained in the project evidence.

### Execution and failure handling

The migration runner uses a transaction for the migration script and ledger
entry. On error it rolls that transaction back and closes its connection. The
five-station seed follows migration and is idempotent; a seed anomaly stops the
run for investigation rather than permitting manual data edits.

On any migration, seed, permission, integrity, or application-boundary failure:

- stop the run; do not retry blindly or make ad hoc SQL repairs;
- record a content-free failure class, migration artifact identity, UTC time,
  and whether rollback was confirmed;
- compare the observed ledger/integrity state with the approved recovery point;
- have the named owner decide between an approved correction/rehearsal or an
  approved recovery procedure; and
- do not start the runtime or operator application as a workaround.

For the first clean staging activation, restoration or recreation of a
discardable recovery target is a separate recovery decision, not an automatic
side effect of migration failure.

### Post-migration evidence

The approved M2.2 report must show, without sensitive or raw database details:

- exactly the approved migration artifact is recorded once;
- five expected stable station identities are present and no station boundary
  was broadened;
- the migrator and runtime identities retain distinct privileges;
- migration-safe repository/API checks pass against the approved boundary;
- no SQLite live fallback, runtime process, media import, or public listener
  exists; and
- any anomaly, recovery decision, and residual risk has an owner and next
  approval gate.

## Compose staging design boundary

The existing Compose design is a pinned PostgreSQL image with a named data
volume and a loopback-only host port. M2.3 may validate a separately deployable
staging arrangement only after M2.2 acceptance. Its boundary is:

- database service isolation and persisted-volume lifecycle are explicit;
- runtime and migrator receive distinct opaque secret references;
- no credential-bearing environment file is committed;
- no public port, reverse proxy, browser exposure, Icecast, source encoder, or
  audio runtime is added; and
- service health evidence is kept separate from application, backup, and
  runtime claims.

M2.1 does not run Compose, inspect a container runtime, or validate the
configuration against an environment.

## Backup, restore, and disaster-recovery plan

M2.4 will validate a backup and controlled restore only after separate approval.
The initial planning targets are a maximum 24-hour recovery-point objective
(RPO) and a four-hour recovery-time objective (RTO) to an application-ready,
non-public recovery target. They are targets for rehearsal, not service-level
promises; the owner must accept or revise them before M2.4 execution.

The required DR evidence is:

1. backup integrity verification and protected artifact inventory;
2. a restore into an isolated, approved non-production target;
3. timed recovery measurement against the accepted RTO/RPO targets;
4. migration-ledger, stable-station, station-isolation, role-boundary, and
   application-readiness checks after restoration;
5. proof that no credentials, programming content, media, raw SQL, or private
   host details entered the evidence record; and
6. documented recovery limitations, a remediation owner, and an explicit DR
   signoff recommendation.

No backup or restore operation is authorized by this plan.

M2 completion does not authorize M3, media work, runtime work, or any
production activity.

## Explicit exclusions

M2.1–M2.4 exclude production access; legacy host/media access; media
ingestion/analysis; scheduling execution; playout, DSP, or automation; source
encoding; Icecast, SHOUTcast, relays, or listener services; public networking;
and any unapproved deployment. The four architectural planes remain decoupled
throughout.
