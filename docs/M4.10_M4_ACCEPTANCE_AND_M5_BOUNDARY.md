# M4.10 M4 Acceptance and M5 Boundary

## Decision

**Status: accepted 2026-08-05 UTC; local-only and non-operational.** This
decision accepts M4.1–M4.9 as deterministic Programming Control Plane
contracts and fixture boundaries: schedule state/versioning, catalog
eligibility, civil templates, separation, dry-run preview, approval,
versioned-publication/rollback modeling, safe API/UI visibility, and local
validation/rehearsal proposal.

Accepted evidence is content-free and station-scoped. It proves `id +
station_id` handling, `not_found` public isolation,
`station_reference_forbidden` internal mismatch handling, deterministic input
and idempotency behavior, immutable artifacts, rollback posture, CSRF/RBAC
safe errors, accessibility/unavailable UI, and no downstream adapter.

`Published (Versioned)` is not `Executed (Runtime)`. No M4 artifact authorizes
or starts M5 runtime, playout, DSP, media access, encoder, relay, Icecast,
listener, DNS, deployment, staging execution, or production activity.

## Open-risk ownership and handoff

M5 may later consume only a separately approved, verified published artifact
through a new versioned contract. The runtime owner must reject missing,
cross-station, incompatible, or stale artifacts and must never infer a
schedule. The M4 publication owner retains rollback/forward-fix ownership;
the M5 owner owns runtime consumption safety. Any operational rehearsal remains
separately authorized under M4.9.

## Next gate

M5.1 was subsequently approved, completed, and accepted as the local-only
[runtime architecture, authority, and Control Plane boundary](M5.1_RUNTIME_ARCHITECTURE_AUTHORITY_AND_CONTROL_PLANE_BOUNDARY.md).
It creates no runtime execution capability. **M5.2 — Published-schedule
consumption contract** is now the next milestone and requires a new explicit
owner authorization.
