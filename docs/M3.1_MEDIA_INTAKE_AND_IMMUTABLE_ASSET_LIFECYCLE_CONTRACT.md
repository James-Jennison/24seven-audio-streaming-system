# M3.1 Media Intake and Immutable Asset-Lifecycle Contract

## Status, purpose, and authority

**Status: local documentation/planning contract; non-operational.** M3.1
defines the authoritative station-scoped asset-lifecycle boundary for the
Programming Control Plane. It does not authorize a migration, database
connection, source-reference use, file access, media intake, worker,
subprocess, provider request, playout, encoder, Icecast action, deployment, or
production change.

This contract is the current execution record for [M3.1 in the authoritative
roadmap](ROADMAP.md#M31--scope-authority-and-asset-lifecycle-contract). It
implements no later roadmap item. Completion of M3.1 does not authorize M3.2
or any other milestone; the owner must explicitly approve one bounded next
sub-milestone.

## Separate state machines

Programming and asset lifecycle are independent. No asset state advances the
programming state machine, and no programming mutation starts an asset action.

| Concern            | Authoritative states                                                                                                 | Meaning                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Programming        | `Proposed/Preview (Dry-Run) → Approved → Published (Versioned) → Executed (Runtime)`                                 | M4 and M5 own later publication/execution boundaries.                                                                     |
| M3 asset lifecycle | `proposed → validated → approved_for_processing → processing → analyzed → metadata_pending → ready_for_schedule_use` | Control-plane asset eligibility only; it never means published, queued, playing, encoded, mounted, or listener-available. |

Asset terminal/recovery branches are `rejected`, `quarantined`, `failed`, and
`superseded`. A retry returns only from `failed` or `quarantined` to
`validated`; it requires explicit operator action and a new bounded attempt.

### Asset-state meanings

| State                     | Meaning                                                                         | Explicitly does not mean                                                   |
| ------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `proposed`                | An intake request is recorded for review.                                       | Source access, upload, processing, or schedule use.                        |
| `validated`               | The request’s safe references and policy fields pass local validation.          | Approval, processing, metadata lookup, or schedule publication.            |
| `approved_for_processing` | An authorized operator permits a future bounded processing attempt.             | Worker launch, file access, provider call, or runtime action.              |
| `processing`              | Reserved only for a future separately authorized worker attempt.                | Playout, DSP application, encoder output, or listener availability.        |
| `analyzed`                | A future bounded analysis result is attached to an immutable revision.          | Operator acceptance, metadata resolution, or executable cue/gain settings. |
| `metadata_pending`        | Candidate metadata awaits operator resolution.                                  | Automatic overwrite or network provider authorization.                     |
| `ready_for_schedule_use`  | The immutable asset revision is eligible for later M4 catalog consideration.    | M4 publication, M5 execution, M7 encoding, or Icecast mount availability.  |
| `rejected`                | The proposal is intentionally declined.                                         | Deletion of provenance or an implicit retry.                               |
| `quarantined`             | A safe category requires investigation before revalidation.                     | Inspection of untrusted media or path disclosure.                          |
| `failed`                  | A bounded future attempt ended with a safe failure category.                    | Automatic retry, fallback source use, or repair.                           |
| `superseded`              | A later immutable revision replaces an earlier revision for future eligibility. | Mutation or erasure of the earlier revision/provenance.                    |

## Station-scoped conceptual model

All conceptual entities carry a stable opaque `id` and `station_id`. Every
future query, command, API reference, audit event, and relationship must use
both values. A cross-station reference or relationship fails with
`station_reference_forbidden`; a missing or out-of-scope entity fails with
`not_found` without disclosing ownership.

| Entity                                    | Required relationship and purpose                                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Intake proposal/request                   | Belongs to one station; contains an opaque idempotency key and one safe source reference.                                                   |
| Intake job                                | Belongs to the request’s station and represents an approved future processing attempt only.                                                 |
| Safe opaque source reference              | A station-scoped non-path, non-filename, non-URL handle. It is resolved only by a later separately approved boundary.                       |
| Asset record                              | Immutable identity for the station-scoped asset lineage; carries lifecycle eligibility, never a raw media location.                         |
| Asset revision and provenance             | Append-only immutable revision linked to its asset and station; provenance is an opaque reference plus safe integrity/reference categories. |
| Processing/analysis result                | Immutable station-scoped result linked to one revision; preserves measured facts separately from derived recommendations.                   |
| Metadata candidate                        | Immutable candidate/provenance record linked to one revision with confidence and pending/approved/rejected resolution state.                |
| Operator resolution                       | Append-only operator decision linked to a candidate; it cannot overwrite an approved revision.                                              |
| Rejection/quarantine/failure/retry record | Station-scoped lifecycle outcome with safe category, retry eligibility, safe timing, and opaque IDs only.                                   |

Future foreign keys and repository checks must reject any asset, revision, job,
result, candidate, or resolution whose `station_id` differs from its parent.
No global asset lookup may be used as a substitute for station-scoped access.

## Immutability, idempotency, and authority

- Asset revisions, provenance, processing results, metadata candidates, and
  operator resolutions are append-only. A future correction creates a new
  immutable revision or resolution record; it never mutates an approved asset
  revision in place.
- An intake request must include a station-scoped opaque idempotency key.
  Repeating the same key for the same station returns the same request/job
  outcome; the same key in a different station is unrelated. Duplicate handling
  must not initiate another processing attempt.
- A retry is a named lifecycle transition from `failed` or `quarantined` to
  `validated`, followed by normal review. It must retain prior safe failure
  evidence and must not implicitly reuse an unverified source.
- Operator validation, approval, rejection, quarantine release, and metadata
  resolution are explicit authorized actions. `approved_for_processing` is a
  permission record only and does not dispatch a worker or any other plane.
- No M3 record can change M4 schedule state, M5 runtime state, M7 encoder
  state, a relay, mount, or listener-facing service.

## Content-free audit and evidence contract

An M3 audit or evidence record may contain only action type, station ID, opaque
entity ID, lifecycle state or safe failure category, safe UTC timing, and safe
count fields. It must never contain media contents, titles, artist names,
filenames, paths, tags, binary data, source payloads, credentials, tokens,
CSRF values, provider payloads, raw SQL, or unredacted error text.

Rejection and failure evidence must report a controlled category, not a raw
exception. Diagnostics that cannot remain content-free stop the action and are
handled outside project evidence under a separately approved process.

## Four-plane separation

| Plane                         | M3.1 authority                                                                            | Prohibited M3.1 effect                                                                        |
| ----------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Programming Control Plane     | Records requests, decisions, and immutable conceptual lifecycle/provenance state.         | File processing, playout, schedule execution, encoder/relay/mount change, or listener action. |
| Playout & Automation Runtime  | None in M3.1. A future M5 runtime may consume only later approved M4 Published artifacts. | Writing M3 intake state or treating asset readiness as execution.                             |
| Source Encoder Layer          | None in M3.1. A future M7 encoder may consume only approved M5 runtime output.            | Asset intake, media analysis, or reading a Control Plane mutation as an encoder command.      |
| Listener-Facing Icecast Layer | None in M3.1. Icecast 2.x remains the future listener-facing platform.                    | Mount, relay, listener, or metadata action from an M3 request.                                |

The control plane must have no route, adapter, credential, or dispatch path
that can directly cause any prohibited effect. PostgreSQL remains the sole
future live persistence target; this contract introduces no SQLite, SAM, PAL,
or SHOUTcast dependency.
