# M3.10 Separately Authorized Staging Activation/Rehearsal Proposal

## Status, purpose, and non-authority

**Status: completed 2026-08-04 UTC; local-only proposal; non-operational.**
M3.10 defines a review-only, station-scoped proposal contract for a future,
bounded staging rehearsal of the M3 persistence and disabled worker boundary.
It does not authorize, schedule, or perform that rehearsal.

This is the implementation and acceptance record for [M3.10 in the
authoritative roadmap](ROADMAP.md#m310--separately-authorized-staging-activationrehearsal-proposal).
It depends on M3.1–M3.9. A future executable rehearsal still requires a new,
separate owner authorization that names the exact reviewed artifact, isolated
target classification, authority categories, change window, evidence boundary,
and stop decision owner. No authorization value, credential, target location,
or protected reference is recorded here.

## Defined proposal contract

`M3StagingRehearsalProposal` is an in-memory TypeScript contract with no route,
adapter, persistence, process, network, or filesystem integration. It requires
only content-free values:

- a station-scoped proposal `id + station_id`, a reviewed commit identity, and
  an opaque migration identity;
- `proposal_only` mode with authorization explicitly required and explicitly
  not granted;
- an isolated-staging, loopback-only, empty/non-production target
  classification, never an address, port, volume, database, path, or DSN;
- distinct migration, Control Plane, future-worker, and evidence-review
  authority categories;
- the existing M3.4 declared sandbox limit contract, which remains a contract
  value and does not configure or start a sandbox;
- explicit inactive M4 publication, M5 runtime, and M7 encoder/listener
  planes; and
- fail-closed stop categories for target ambiguity, missing authority,
  unexpected input, and plane activation. Automatic retry and rollback are
  prohibited; the next action is always an owner decision.

The review-only boundary can return a station-scoped `execution: unavailable`,
`rehearsalPerformed: false`, and `evidenceStatus: not_run` result. It can also
model the safe stop/cleanup decision shape with `cleanup: not_started`; it
cannot start a rehearsal, execute cleanup, or generate live evidence.

## Future acceptance evidence requirements

Any separately authorized execution must provide only content-free pass/fail
evidence for these categories:

| Future verification category   | Required bounded result                                                                   |
| ------------------------------ | ----------------------------------------------------------------------------------------- |
| Ledger/schema                  | Reviewed migration/ledger and expected schema fact pass/fail without raw SQL or row data. |
| Station isolation              | `id + station_id`, `not_found`, and `station_reference_forbidden` probe outcome only.     |
| No network/downstream dispatch | Worker, provider, runtime, encoder, relay, and Icecast invocation result: no dispatch.    |
| Stop/cleanup                   | Stop category, cleanup result, and owner decision reference only.                         |

The local proposal and its tests do not claim that any of these future probes
ran. They define the required evidence shape and reject execution authority.

## Acceptance criteria and local evidence

| Criterion                             | Local evidence                                                                                                                          |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Reviewed identity and least privilege | Validation requires a commit identity, opaque migration identity, and distinct authority categories.                                    |
| Isolated, empty target                | Validation admits only isolated-staging, loopback-only, empty/non-production classification.                                            |
| Sandbox limits and inactive planes    | The established M3.4 limits are required as data only; M4/M5/M7 values must be inactive.                                                |
| Station isolation                     | Public other-station review returns `not_found`; internal mismatch returns `station_reference_forbidden`.                               |
| Recovery/rollback                     | A stop decision is fail-closed, performs no cleanup, and requires an owner decision without automatic retry or rollback.                |
| Content-free evidence                 | Proposal/review/stop serialization has no content-bearing, credential, CSRF, or SQL field.                                              |
| No operational side effects           | Static tests prove no process, filesystem, network, or HTTP adapter import/call; review remains unavailable and not run.                |
| Accessibility/non-operational UI      | Existing dashboard tests preserve explicit fixture labeling, `aria-disabled` unavailable affordances, and no rehearsal/staging control. |

## Explicit exclusions and operational boundary

M3.10 creates no migration, database connection, persistence activation,
container, worker, subprocess, sandbox, parser, FFmpeg or other media tool. It
does not access media or arbitrary paths, call a provider, contact runtime,
encoder, relay, or Icecast systems, expose a listener, deploy, or alter
infrastructure. PostgreSQL remains the sole future live persistence target;
SQLite is not introduced.

The Programming Control Plane, Playout & Automation Runtime, Source Encoder
Layer, and Listener-Facing Icecast Layer remain separately deployable and
strictly decoupled. This proposal adds no UI/API action and cannot imply or
perform media intake, scheduling, publication, playout, DSP, encoding, relay,
or listener-facing control. All records use `id + station_id`, and all local
evidence remains content-free.
