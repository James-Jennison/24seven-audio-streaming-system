# M3.11 M3 Acceptance and Handoff Boundary

## Status, purpose, and non-authority

**Status: completed 2026-08-04 UTC; local-only acceptance decision;
non-operational.** M3.11 records the decision-only acceptance assessment for
the completed M3 Programming Control Plane contracts and their disabled
boundaries. It is based on local evidence review only; it does not claim a
staging rehearsal occurred.

This is the implementation and acceptance record for [M3.11 in the
authoritative roadmap](ROADMAP.md#m311--m3-acceptance-and-handoff-boundary).
It depends on the accepted M3.1–M3.10 records. Acceptance is not operational
authority: it does not activate M4, M5, M7, production, persistence, or any
other plane.

## Accepted local boundary

`M3AcceptanceHandoff` is an in-memory, station-scoped TypeScript contract
that can record only an `accepted_for_handoff` decision with
`operationalAuthority: not_granted`. It requires all M3.1–M3.10 acceptance
identities plus exactly these content-free local evidence categories:

- content-free local evidence;
- station-isolation results; and
- disabled-boundary results.

Every handoff, evidence item, and open-risk ownership record carries `id +
station_id`. Public review of a missing or other-station handoff returns
`not_found`; a trusted internal station mismatch returns
`station_reference_forbidden`. Evidence and risk records contain only opaque
IDs, station IDs, safe categories, bounded decision states, and opaque owner
references. They contain no programming payload, media content, title,
filename, path, URL, metadata payload, credential, token, CSRF value, or raw
SQL.

The contract requires at least one owned open risk. The two acceptance risks
remain open: later-milestone approval is required, and operational authority
has not been granted. This records ownership without naming a person, service,
credential, target, or implementation instruction.

## Asset-readiness and plane boundary

The M3 acceptance decision confirms that `ready_for_schedule_use` is asset
eligibility only. In the handoff contract it requires all of the following:

| Concern                       | Required M3.11 decision state |
| ----------------------------- | ----------------------------- |
| Asset readiness               | `ready_for_schedule_use`      |
| Schedule or publication       | `not_published`               |
| Playout & Automation Runtime  | `unavailable`                 |
| Source Encoder Layer          | `unavailable`                 |
| Listener-Facing Icecast Layer | `unavailable`                 |

The Programming Control Plane, Playout & Automation Runtime, Source Encoder
Layer, and Listener-Facing Icecast Layer therefore remain separately deployable
and strictly decoupled. No dashboard or API action is added or changed by
M3.11. The existing dashboard remains fixture/example-only, accessible, and
non-interactive for unavailable future planes.

## Explicit exclusions and operational proof

M3.11 creates no migration and does not connect to or activate persistence.
It starts no container, worker, subprocess, FFmpeg, parser, media tool, or
service; accesses no real media, source reference, or filesystem path; calls no
provider; and contacts no runtime, encoder, relay, or Icecast system. It does
not deploy, alter infrastructure, or perform a production action.

PostgreSQL remains the sole future live persistence target; SQLite is not
introduced. Windows, SAM, PAL, SHOUTcast, arbitrary process control, and
external-system control are not introduced. The local-only dashboard/API
boundary continues to make no implicit ingestion, processing, scheduling,
publication, playout, DSP, encoder, relay, or listener-facing request.
