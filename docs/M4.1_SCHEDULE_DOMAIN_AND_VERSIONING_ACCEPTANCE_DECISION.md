# M4.1 Schedule-Domain and Versioning Acceptance Decision

## Decision and boundary

**Status: accepted 2026-08-05 UTC; local documentation/planning only.** This
decision accepts [M4.1's schedule-domain and versioning
contract](M4.1_SCHEDULE_DOMAIN_AND_VERSIONING_CONTRACT.md) as the complete
first M4 sub-milestone under the separate owner authorization to begin M4.

It accepts only a conceptual Control Plane boundary. It authorizes no M4.2
catalog work, schema, migration, database connection, API, UI, proposal,
approval workflow, publication, runtime consumption, encoder, Icecast,
deployment, or production activity.

## Review evidence

| Required M4.1 criterion | Accepted review outcome                                                                                                                                                                            |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| State separation        | `Proposed/Preview → Approved → Published` is separate from the future M5 `Published → Executed` boundary. Publication is never execution.                                                          |
| Station isolation       | Every conceptual entity, reference, query, command, and audit record requires `id + station_id`; out-of-scope resources are `not_found` and internal mismatches are `station_reference_forbidden`. |
| Versioning and rollback | Published versions are immutable and append-only. Rollback changes only one station-scoped active pointer to a prior immutable version.                                                            |
| Evidence safety         | Audit/evidence is limited to opaque IDs, states, safe categories, UTC timing, and counts; schedule content and sensitive data are prohibited.                                                      |
| Plane separation        | M4.1 defines only Control Plane contracts. It adds no runtime, source-encoder, relay, Icecast, listener, filesystem, media, provider, persistence, or deployment path.                             |
| M3 handoff              | M3 `ready_for_schedule_use` remains input-only eligibility. M4 cannot advance or reinterpret the M3 lifecycle.                                                                                     |
| Future gates            | M4.2–M4.10 retain their individually approval-gated boundaries; M5 remains unapproved.                                                                                                             |

The review reconciles the accepted M1, M2, and M3 records and the
[authoritative roadmap](ROADMAP.md). It found no state definition that treats
publication as execution and no contract that weakens station isolation or
content-free evidence requirements.

## Explicit exclusions and operational proof

This decision creates no executable capability. It performed no filesystem or
media access, PostgreSQL connection, migration, container, worker, subprocess,
provider call, network operation, scheduling, publication, playout, DSP,
encoder, relay, Icecast, DNS, deployment, or production action. PostgreSQL
remains the sole future live persistence target; SQLite, Windows, SAM, PAL,
legacy SHOUTcast, and arbitrary process control are not introduced.

The Programming Control Plane, Playout & Automation Runtime, Source Encoder
Layer, and Listener-Facing Icecast Layer remain strictly decoupled and
separately deployable. No dashboard or API action can invoke an M4 action as a
result of this decision.

## Next gate

At the time of this decision, **M4.2 — Catalog and asset-eligibility boundary**
was the next sequential milestone and required a new, explicit owner approval.
This M4.1 decision did not itself grant or imply that approval.
