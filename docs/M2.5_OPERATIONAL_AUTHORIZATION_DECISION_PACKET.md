# M2.5 Operational-Authorization Decision Packet

## Status and authority

**Status: published planning and decision-support artifact (`b07814d`),
non-operational.** This packet turned the then-unresolved decisions from the
published M2.1–M2.4 plans into one owner-review checklist. Completing,
reviewing, or publishing this document did not authorize an operational action.

It does not authorize infrastructure or database connections, secret access,
Docker or Compose, containers, services, migrations, topology probes, backup,
restore, DR rehearsal, deployment, or media, playout, runtime, encoder, relay,
Icecast, SHOUTcast, or listener-facing activity. Each M2 gate required
separate, explicit owner approval.

Except where explicitly marked historical below, this packet records the
pre-execution decision boundary. The M2 outcome is now formally accepted in
the [M2 acceptance and staging-readiness decision](M2_ACCEPTANCE_AND_STAGING_READINESS_DECISION.md);
the next approval gate is M3.1 planning only.

The packet preserves PostgreSQL as the sole live persistence store; SQLite and
`m1-store` remain test-only. The programming control plane, playout runtime,
source encoder layer, and listener-facing Icecast layer remain decoupled and
separately deployable. Every future application validation must preserve
`id + station_id` isolation, `not_found`, `station_reference_forbidden`, and
content-free audit/evidence requirements.

## How the owner uses this packet

For each field, record an approval decision and a safe external decision or
evidence reference. Do not record target addresses, DSNs, credentials, keys,
tokens, secret-reference paths, backup locations, volume identifiers, raw SQL,
or database/programming content in this repository. An unanswered, rejected,
ambiguous, or externally inconsistent field is a stop condition for its gate.

### Shared decision fields

| Field               | Owner decision required before an operational gate                                                | Safe record boundary                                                |
| ------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Reviewed artifact   | Exact reviewed Git commit/build and migration artifact                                            | Commit/build identifier only                                        |
| Staging boundary    | Named staging classification, approved operator, and change window                                | External decision reference; no host or network detail              |
| Authorities         | Accountable owner, platform, migration, runtime, backup, restore, and evidence-review authorities | Authority class and decision reference only                         |
| Least privilege     | Schema ownership, migration, runtime DML, backup, restore, and platform role/grant separation     | Reviewed role/grant artifact reference; no grant SQL or credentials |
| Extension authority | Named authority and approved timing for `pgcrypto` installation/verification                      | Authority class and pass/fail only                                  |
| Transport/version   | Accepted PostgreSQL version/image identity and approved transport/TLS policy                      | Policy/version outcome only; no endpoint or certificate detail      |
| Evidence            | Approved content-free probe set, reviewer, retention/access policy, and safe evidence location    | Opaque external reference and pass/fail results only                |
| Recovery targets    | Owner acceptance or revision of the proposed 24-hour RPO and four-hour RTO                        | Decision and measured-duration policy only                          |

No privileged identity may be shared or substituted between platform,
migration, runtime, backup, restore, or evidence-review duties.

## Gate 1 — M2.2 migration execution

**Requires a separate migration-execution approval.** The approval must name
the reviewed artifact, staging classification, approved operator, change
window, recovery decision owner, and safe evidence location outside this
repository.

| Decision field        | Required owner decision or artifact                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Target and window     | Confirm the isolated non-public staging boundary and approved change window.                                                                                                         |
| Authority and grants  | Approve the reviewed least-privilege ownership/grant artifact: platform authority, migration authority, and runtime DML identity must be separate.                                   |
| `pgcrypto`            | Approve the platform/extension authority responsible for availability before `002_m1_control_plane.sql` is applied.                                                                  |
| Version and transport | Accept the PostgreSQL version/image identity and transport/TLS policy before connection.                                                                                             |
| Pre-change recovery   | Resolve the recovery-point method, integrity evidence, decision owner, and safe evidence location. A later M2.4 backup cannot be assumed to satisfy this prerequisite retroactively. |
| Probe contract        | Approve content-free checks for the migration ledger, schema/extension readiness, five stable stations, role boundary, and station isolation.                                        |
| Failure decision      | Approve the transaction/ledger failure, seed-failure, stop, and escalation path; no ad hoc SQL, grants, retry, or recovery action.                                                   |

The reviewed runner applies only `002_m1_control_plane.sql` and then the
idempotent five-station seed. A seed failure, missing extension authority,
missing recovery decision, or missing probe contract stops the gate.

## Gate 2 — M2.3 topology validation

**Requires a separate topology-validation approval after M2.2 evidence, or a
separately approved bounded alternative.** It authorizes observation only, not
migration, backup, restore, or service expansion.

| Decision field       | Required owner decision or artifact                                                                                                                                               |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deployment placement | Accept whether PostgreSQL and the future loopback-only control-plane process are host or container responsibilities, and their permitted local connectivity.                      |
| Image and lifecycle  | Approve image provenance/immutable identity policy, accepted PostgreSQL version, vulnerability-review expectation, and capacity/retention responsibility.                         |
| Exposure             | Confirm loopback-only PostgreSQL and control-plane exposure; prohibit public listeners, tunnels, proxies, and firewall exceptions.                                                |
| Volumes and restart  | Approve persistent-volume ownership/lifecycle, source/target separation, capacity evidence, and whether `restart: unless-stopped` is acceptable.                                  |
| Role separation      | Confirm platform, migration, runtime, backup, and restore identities remain distinct and runtime has no DDL, extension, ledger, or backup authority.                              |
| Probe contract       | Approve content-free topology probes for version/transport, bindings, image/volume boundary, role separation, station isolation, application compatibility, and plane decoupling. |
| Stop/escalation      | Define escalation if observed placement, exposure, image, volume, identity, or restart behavior differs from the accepted topology.                                               |

Playout, source encoding, and Icecast remain absent from M2 topology scope and
receive no database or network authority.

## Gate 3 — backup creation and verification

**Requires a separate backup-only approval after passed M2.2/M2.3 evidence, or
an explicitly approved limited alternative.** It does not authorize restore.

| Decision field      | Required owner decision or artifact                                                                                                     |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Recovery method     | Select the backup method/tool/format and consistency boundary; do not assume logical and volume recovery are interchangeable.           |
| Artifact protection | Approve artifact classification, integrity method, retention, access control, protected handling, and evidence retention/access policy. |
| Authority           | Name the backup authority, separate from migration, runtime, platform, and restore authorities.                                         |
| RPO                 | Accept or revise the 24-hour RPO target and measurement definition before backup verification.                                          |
| Source boundary     | Confirm staging-only source, approved operator/window, and no included credentials, host configuration, media, or listener data.        |
| Evidence            | Approve content-free integrity, completeness, recovery-point timestamp, retention, and safe-failure evidence.                           |

Failure to create or verify the artifact stops the process. It does not permit a
restore, an automatic retry, or a substitute method.

## Gate 4 — restore rehearsal

**Requires a separate restore-only approval after an approved, verified backup
exists.** It never permits source or production overwrite.

| Decision field     | Required owner decision or artifact                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Recovery target    | Approve an isolated, non-public, non-production target distinct from the staging source and define the destructive-action boundary.                                                                |
| Restore method     | Select the compatible logical or volume/database restore method; no method switch occurs without a new owner decision.                                                                             |
| Authority          | Name separate platform, restore, and evidence authorities; runtime remains excluded from restore authority.                                                                                        |
| RTO                | Accept or revise the four-hour RTO target, its measurement start/end, and the failure-class treatment.                                                                                             |
| Validation         | Approve content-free recovery checks for migration ledger/schema, five stable stations, station isolation, role separation, volume lifecycle, application compatibility, and safe failure closure. |
| Evidence retention | Approve who can review the content-free evidence, for how long, and how residual risks/owner decisions are recorded.                                                                               |

Any unknown target, potential overwrite, failed validation, or leaked evidence
is a stop and escalation condition. Transaction rollback is not a backup or
restore substitute.

## Required order and current stop condition

The operational sequence is fixed:

```text
M2.2 migration execution
  → M2.3 topology validation
  → M2.4 backup creation/verification
  → M2.4 restore rehearsal
  → M2 acceptance
```

No gate was implied by a previous gate, by this packet, or by a documentation
commit. The historical stop condition was unresolved owner decisions and the
absence of the reviewed role/grant, extension-authority, recovery-point,
topology, backup-method, recovery-target, probe, and evidence-retention
artifacts described above. Those independent M2 gates were subsequently
completed under separate approvals; the formal outcome is recorded in the
[M2 acceptance and staging-readiness decision](M2_ACCEPTANCE_AND_STAGING_READINESS_DECISION.md).
