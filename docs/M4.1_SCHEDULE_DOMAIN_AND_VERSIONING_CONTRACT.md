# M4.1 Schedule-Domain and Versioning Contract

## Status, purpose, and authority

**Status: accepted local documentation/planning contract; non-operational.** M4.1
defines the authoritative station-scoped schedule, proposal, approval,
publication, version, compatibility, and rollback boundary for the
Programming Control Plane. It does not authorize a migration, database
connection, catalog query, clock/template implementation, policy engine,
approval workflow, publication, runtime consumption, encoder, Icecast action,
deployment, or production change.

This contract is the current execution record for [M4.1 in the authoritative
roadmap](ROADMAP.md#m41--schedule-domain-and-versioning-contract). It
implements no later roadmap item. Completion of M4.1 does not authorize M4.2
or any other milestone; the owner must explicitly approve one bounded next
sub-milestone, per [the roadmap's approval and completion
policy](ROADMAP.md#approval-and-completion-policy).

## Separate state machines

Programming and asset lifecycle remain independent, as established in M3.1.
M4.1 owns only the non-runtime portion of the Programming state machine.

| Concern                  | Authoritative states                                            | Meaning                                                                                                 |
| ------------------------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Programming (M4 portion) | `Proposed/Preview (Dry-Run) → Approved → Published (Versioned)` | M4 owns definition, review, and immutable versioned publication only.                                   |
| Programming (M5 portion) | `Published (Versioned) → Executed (Runtime)`                    | A future, separately approved M5 runtime owns execution; M4.1 defines no execution behavior.            |
| M3 asset lifecycle       | `... → ready_for_schedule_use` (terminal for M4 purposes)       | M4 may reference only this eligibility state; it never advances or reinterprets the M3 asset lifecycle. |

Programming terminal/recovery branches relevant to M4.1 are `rejected` (a
proposal is not approved) and `rolled_back` (a later published version
replaces an earlier one for the _active_ pointer only — see below). Neither
branch mutates or erases an earlier immutable published version.

### Programming-state meanings (M4.1 scope)

| State                  | Meaning                                                                       | Explicitly does not mean                                                   |
| ---------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `proposed` / `preview` | A dry-run schedule candidate is generated or recorded for review.             | Approval, publication, or any runtime/encoder/listener effect.             |
| `approved`             | An authorized reviewer accepts a specific, immutable set of reviewed inputs.  | Publication, versioning, or runtime consumption.                           |
| `published`            | An approved schedule becomes an immutable, station-scoped versioned artifact. | Playout, queue mutation, encoder output, relay, mount, or listener change. |
| `rolled_back`          | The _active_ published pointer for a station returns to a prior version.      | Deletion of the rolled-back version or any runtime action.                 |
| `rejected`             | A proposal is intentionally declined at review.                               | Deletion of the proposal or an implicit new proposal.                      |

## Station-scoped conceptual model

All conceptual entities carry a stable opaque `id` and `station_id`. Every
future query, command, API reference, audit event, and relationship must use
both values. A cross-station reference or relationship fails with
`station_reference_forbidden`; a missing or out-of-scope entity fails with
`not_found` without disclosing ownership — the same rule M3.1 established.

| Entity                      | Required relationship and purpose                                                                                                                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Schedule proposal / preview | Belongs to one station; a dry-run candidate built from M3 `ready_for_schedule_use` references, a clock/template, and a policy set (M4.2–M4.5 inputs, not defined here). |
| Approval record             | Append-only decision linked to one proposal; requires an authorized station-scoped reviewer identity.                                                                   |
| Published version           | Immutable, station-scoped, monotonically identified artifact created only from an `approved` proposal.                                                                  |
| Active-version pointer      | Station-scoped pointer to exactly one published version; the only mutable element, and only via `publish` or `rollback`.                                                |
| Compatibility record        | Immutable statement of whether a published version's referenced asset/catalog inputs remain valid, without altering the version.                                        |
| Rollback record             | Append-only decision linking an active-version change to a prior, still-immutable published version.                                                                    |

Future foreign keys and repository checks must reject any proposal, approval,
version, compatibility record, or rollback record whose `station_id` differs
from its parent. No global schedule lookup may substitute for station-scoped
access.

## Immutability, idempotency, and authority

- Proposals, approvals, published versions, compatibility records, and
  rollback records are append-only. A correction creates a new proposal,
  approval, or published version; it never mutates an approved proposal or a
  published version in place.
- A proposal-generation request must include a station-scoped opaque
  idempotency key. Repeating the same key for the same station returns the
  same proposal outcome; the same key in a different station is unrelated.
- `Published` version identity is permanent once created. `rollback` changes
  only the active-version pointer to a prior published version; it does not
  delete, mutate, or renumber any published version.
- Approval and publication are explicit authorized actions requiring
  station-scoped reviewer/publisher identity, CSRF, and RBAC (defined fully
  in M4.6/M4.8). `Approved` is a decision record only and does not itself
  publish.
- No M4 record can start playout, mutate a runtime queue, drive an encoder,
  touch a relay/mount, or reach a listener. Publication is never execution —
  this is the single hardest constraint of M4.1 and binds every later M4
  sub-milestone.
- No M4 record can mutate the M3 asset lifecycle. M4 may only read
  `ready_for_schedule_use` asset references; it has no write path into M3.

## Content-free audit and evidence contract

An M4 audit or evidence record may contain only action type, station ID,
opaque entity ID, lifecycle state, version identity, safe rejection/rollback
category, safe UTC timing, and safe count fields. It must never contain
schedule content (track/asset titles, artist names, filenames, paths), CSRF
values, credentials, tokens, raw SQL, or unredacted error text — the same
content-free rule M3.1 through M3.12 applied throughout.

Rejection, rollback, and compatibility-failure evidence must report a
controlled category, not a raw exception.

## Four-plane separation

| Plane                         | M4.1 authority                                                                                   | Prohibited M4.1 effect                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| Programming Control Plane     | Defines proposal, approval, publication, versioning, compatibility, and rollback contracts only. | Any file processing, playout, encoder/relay/mount change, or listener action.        |
| Playout & Automation Runtime  | None in M4.1. A future M5 runtime may consume only later approved, Published M4 artifacts.       | Writing M4 proposal/approval/publication state or treating publication as execution. |
| Source Encoder Layer          | None in M4.1. A future M7 encoder may consume only approved M5 runtime output.                   | Reading a Control Plane publication as an encoder command.                           |
| Listener-Facing Icecast Layer | None in M4.1. Icecast 2.x remains the future listener-facing platform.                           | Mount, relay, listener, or metadata action from an M4 record.                        |

The control plane must have no route, adapter, credential, or dispatch path
that can directly cause any prohibited effect. PostgreSQL remains the sole
future live persistence target; this contract introduces no SQLite, SAM, PAL,
or SHOUTcast dependency.
