# M2.3 Staging Topology Validation Plan

## Status, authority, and separation of gates

**Status: drafted locally for review.** This plan describes future,
non-public topology validation only. It authorizes no staging access, database
connection, migration, Compose invocation, service start, backup, restore,
deployment, or runtime/stream action.

Three future approvals are distinct:

1. **Migration execution approval** permits only the reviewed M2.2 migration
   procedure against the named staging database; it does not validate or start
   topology services.
2. **Topology-validation approval** permits only the named M2.3 checks against
   the accepted staging design; it is not a migration approval and does not
   create a public service.
3. **M2.4 DR approval** permits separately scoped backup/restore rehearsal; it
   is not granted by a successful topology check.

M2 does not implement media ingestion, scheduling execution, playout, DSP,
automation, source encoding, Icecast, SHOUTcast, relays, or listener-facing
services. It does not alter the control-plane state model:

```text
Proposed / Preview → Approved → Published (Versioned) → Executed (Runtime)
```

## Proposed staging topology

The following is a proposed design derived from local repository assets. It is
not a claim about the actual staging environment.

```text
                     platform / provisioning authority
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
     migration authority                     backup / restore
     (approved, short-lived)                 (M2.4 only)
              │                                   │
              └──────────── PostgreSQL ───────────┘
                             persistent volume
                                   │
                       runtime database authority
                                   │
                    Programming Control Plane
                    (future M2.3 validation only)

   Playout & Automation Runtime      Source Encoder      Listener Icecast
       no M2.3 deployment             no M2.3 deployment  no M2.3 deployment
       no PostgreSQL authority         no PostgreSQL       no PostgreSQL
```

The four planes remain independently deployable and decoupled. PostgreSQL is
the sole live persistence direction. The control plane is the only future M2.3
application component that may use the runtime database identity. It has no
authority to signal future playout, encoder, relay, or stream components. The
future playout runtime, source encoder layer, and listener-facing Icecast layer
receive no database identity, database network path, or M2.3 service action.

## Network, host, and service-account boundaries

### Non-public exposure rules

- The PostgreSQL host binding must remain loopback-only. No public port,
  reverse proxy, tunnel, listener, or firewall exception is in M2.3 scope.
- A future control-plane HTTP process must remain loopback-only. Its access
  mechanism, if any, requires separately approved topology scope; it must not
  be treated as public browser exposure.
- Database connectivity may exist only between the approved control-plane
  runtime process and PostgreSQL, and only after the respective M2.2/M2.3 gate.
  Migration, backup, and restore connections are separate, short-lived,
  purpose-bound paths.
- Playout, source encoder, and Icecast components must have no M2.3 network or
  database path. Their future isolation is evaluated in later milestones.

### Identity and persistence boundaries

| Component or authority | Future permitted database/network scope                      | Must not have                                                                                  |
| ---------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Platform/provisioning  | Approved database/role/extension setup only                  | Routine application, migration, or audio/listener use                                          |
| Migration authority    | Named staging database and reviewed migration runner only    | Long-lived runtime, UI, backup/restore, or role changes outside approved setup                 |
| Control-plane runtime  | Named staging database with reviewed runtime DML grants only | DDL, extension, migration-ledger, role, backup/restore, playout, encoder, or Icecast authority |
| Backup authority       | Backup artifact path in M2.4 only                            | Runtime/UI, DDL, production, or audio/listener authority                                       |
| Restore authority      | Isolated recovery target in M2.4 only                        | Production restore, runtime/UI, or unapproved role authority                                   |
| Playout runtime        | No M2.3 database identity or service                         | Control-plane approval/publication authority                                                   |
| Source encoder         | No M2.3 database identity or service                         | Programming/control-plane authority                                                            |
| Icecast listener layer | No M2.3 database identity or service                         | Programming/control-plane authority                                                            |

No privileged shared identity is permitted. A database superuser, migration
identity, runtime identity, backup identity, and restore identity must never be
interchangeable. Secret inputs remain opaque references categorized by platform,
migration, runtime, backup, restore, and evidence access; no values, paths,
DSNs, tokens, certificates, or credential identifiers are recorded here.

## Evidence, audit, and application constraints

All M2.3 evidence is content-free. It may identify the reviewed Git artifact,
component/identity class, station identifier where genuinely required, UTC time,
safe pass/fail outcome, and named approval/recovery decision. It must not store
database content, programming payloads, media data, titles, filenames,
credentials, tokens, CSRF material, raw SQL, query output, DSNs, private
network details, or volume/container identifiers.

Application compatibility validation must preserve all M1 security contracts:
server-side RBAC and CSRF remain authoritative; `m1-store` never enters the
live path; SQLite never becomes a runtime fallback; and station-scoped reads,
mutations, and references use both `id` and `station_id`. Control-plane UI/API
operations remain incapable of directly invoking any audio or listener plane.

## Stop conditions and escalation

Future topology validation must stop before or during the approved activity if:

1. the actual staging target, image identity, database version, transport, or
   host/container model differs from the owner-accepted topology;
2. public exposure, an unapproved listener, an unknown service, or a
   cross-plane network/control path is observed;
3. any identity is shared, over-privileged, unverifiable, or supplied through
   an unapproved secret-reference category;
4. persistent-volume ownership/lifecycle, recovery point, or backup handoff is
   unknown or incompatible with the M2.4 plan;
5. an evidence record would leak sensitive, operational, database, or
   programming information; or
6. a migration, runtime, media, encoder, relay, Icecast, listener, backup, or
   restore action would be required to continue.

The operator records only a safe failure class and stops. The named owner then
chooses one of: accept a revised topology plan, approve a bounded correction,
or defer the milestone. No automatic configuration change, retry, service
start, or recovery action is allowed.

## Prerequisites and unresolved owner decisions

The following must be resolved before any future M2.3 topology-validation
approval, and remain separate from M2.2 migration execution approval:

1. Owner-accepted staging topology: control-plane process placement, container
   versus host boundary, and permitted local connectivity model.
2. Exact PostgreSQL version/image provenance and accepted transport/TLS policy.
3. Reviewed role/grant and ownership artifact, including `pgcrypto`
   installation responsibility.
4. Approved content-free probes for exposure, image/volume boundary, role
   separation, ledger/seed facts, and application compatibility.
5. Persistent-volume owner, lifecycle, capacity, and M2.4 backup handoff.
6. Decision on the current Compose `restart: unless-stopped` behavior.
7. Owner acceptance or revision of the M2.4 24-hour RPO and four-hour RTO
   planning targets.
8. A separately reviewed consistency correction for outdated operator-facing
   README and historical architecture wording before those documents are used
   as operational instructions.
