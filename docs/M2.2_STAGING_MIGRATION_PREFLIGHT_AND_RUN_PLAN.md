# M2.2 Staging Migration Preflight and Run Plan

## Status, authority, and boundary

**Status: drafted locally for review.** This artifact was prepared under the
approved M2.2 preflight/run-plan task. It is not a migration-execution approval
and does not authorize a database connection, VM access, Compose invocation,
service start, backup, restore, deployment, or runtime action.

Any future execution must have a new, explicit M2.2 approval that names the
reviewed Git commit, staging target, approved operator, change window, recovery
decision owner, and safe evidence location. M2.3 and M2.4 remain separately
approval-gated.

M2 only establishes persistence evidence. It cannot alter the control-plane
state boundary, invoke media ingestion, or signal playout, automation, encoder,
relay, Icecast, SHOUTcast, or listener-facing work. PostgreSQL remains the only
live persistence direction; SQLite and `m1-store` remain test-only.

## Target and identity boundary

The eventual target is only the approved, non-public staging database on
`24seven-audio-dev`. This document does not connect to the host or record any
address, key, fingerprint, filesystem path, secret path, credential, DSN, or
provider detail. Local tests are not a staging database; staging is not
production.

| Identity class                  | Required future scope                                                                                                                    | Explicitly prohibited                                                                                                    |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Platform/provisioning authority | Create or select the isolated staging database; manage controlled extensions and identities in an approved setup step                    | Application runtime, routine migration, or ordinary programming work                                                     |
| Migration authority             | Connect only to the named staging database; own/apply the reviewed migration ledger, schema changes, and stable-station seed during M2.2 | Long-lived runtime, UI access, backup/restore operations, or role management outside the approved setup                  |
| Runtime authority               | After separate approval, connect only to the named staging database and perform required application DML                                 | Schema DDL, extension management, migration-ledger writes, role management, cross-database access, or fallback to SQLite |
| Backup authority                | Create approved backup artifacts and verify their integrity in M2.4                                                                      | Runtime/UI use, DDL, role management, or production access                                                               |
| Restore authority               | Restore only into a separately approved, isolated non-production recovery target in M2.4                                                 | Production restore, routine runtime use, or unapproved role changes                                                      |

The future grant review must establish object ownership and the minimum runtime
privileges for users, sessions, audit events, stations, and every
station-scoped programming table. Runtime grants must not broaden the existing
application invariant: every entity query, mutation, and reference is scoped
by `id + station_id`; cross-station references produce
`station_reference_forbidden`; missing or out-of-scope resources produce
`not_found`. Database foreign keys and application SQL checks must remain
consistent with that invariant.

## Preconditions and stop conditions

All of the following must be positively confirmed in the future approved M2.2
run record before the first connection:

1. The current reviewed commit is pinned and its repository checks pass.
2. The named target is the isolated staging database, not local or production.
3. A named human operator, change window, recovery decision owner, and
   access-controlled evidence location are approved.
4. The platform authority has confirmed a compatible PostgreSQL version,
   `pgcrypto` availability, sufficient capacity, UTC clock handling, and
   loopback-only/non-public network boundary without recording sensitive
   details here.
5. The reviewed role/grant plan keeps platform, migration, runtime, backup,
   and restore authorities separate.
6. A verified pre-change recovery point exists; the owner has accepted the
   recovery objective for this run and the future M2.4 target of 24-hour RPO
   and four-hour RTO, or has recorded an approved revision.
7. The approved verification probe can prove only safe pass/fail facts for
   ledger state, station count/identity set, role separation, and application
   boundary without retaining raw SQL, rows, connection details, or content.
8. No Compose, application, browser, runtime, media, encoder, relay, Icecast,
   or listener process will be started under the M2.2 gate.

Failure of any item is a **stop condition**. The operator must not substitute
an identity, bypass a check, make an ad hoc database change, retry repeatedly,
or broaden the approved scope.

## Future execution procedure — not authorized by this task

The following sequence is an exact proposed procedure for a separately
approved M2.2 execution gate. It must not be executed from this documentation
task.

1. Confirm the approved Git commit, the single expected PostgreSQL migration
   (`002_m1_control_plane.sql`), the named staging target classification, and
   the no-public-service boundary.
2. Record content-free preflight pass/fail outcomes for the prerequisites and
   stop if any outcome is not affirmative.
3. Confirm the pre-change recovery point and owner recovery decision authority.
   Do not begin a migration if recovery evidence is absent or stale under the
   accepted objective.
4. Have the approved platform authority confirm extension and role readiness.
   If `pgcrypto` requires a setup action, stop and obtain a separate explicit
   approval for that action; do not grant the runtime additional privilege.
5. Inject only the approved migration connection reference into the reviewed
   migration-runner process. Do not provide the runtime, backup, or restore
   reference to that process.
6. Build the reviewed repository artifact, then invoke the existing migration
   runner with `npm run migrate`. The runner is expected to bootstrap
   `schema_migrations`, apply `002_m1_control_plane.sql` in a transaction,
   record that migration in the ledger, and idempotently seed the five stations.
   Do not start the application after it returns.
7. Close the migration connection and use the separately approved safe
   verification probe to collect only the post-migration evidence in the
   verification matrix below.
8. Stop at the M2.2 decision point. A passing migration does not authorize
   Compose topology validation, runtime connectivity, backup/restore, or M3.

## Rollback versus recovery decision tree

```text
Preflight fails
  → do not connect or mutate; resolve the missing approval/prerequisite.

Runner fails before migration transaction begins
  → stop; note that schema_migrations bootstrap may already exist; use the
    approved probe and recovery decision owner before any further action.

Runner fails during the migration transaction
  → runner attempts rollback and closes; verify only safe ledger/integrity
    facts; do not assume rollback restored every pre-transaction side effect.

Migration commits but station seeding or postflight verification fails
  → stop; the schema may be valid but the staging boundary is not accepted.
    Do not rerun, manually seed, or roll back automatically.

Owner decision after evidence review
  → choose a separately approved correction/rehearsal, or a separately
    approved recovery of a discardable non-production target from the known
    recovery point. Restoration is not assumed safe or automatic.
```

No production rollback exists in M2 scope. A migration rollback is not presumed
safe merely because a transaction is present: extension/bootstrap state, seed
state, and any platform setup require explicit assessment.

## Compose boundary and unresolved repository items

`compose.yaml` is not run by M2.2. Its relevant current properties are a pinned
`postgres:17.5-bookworm` image, named volume, loopback-only host port, and
`restart: unless-stopped`. M2.3 must separately decide whether the restart
policy, volume lifecycle, PostgreSQL version match, and health-check evidence
meet the non-public staging requirements before any invocation.

The following repository/documentation items must be resolved or explicitly
accepted before migration execution:

1. **Grant artifact absent:** no reviewed role/grant definition currently
   exists. The owner must approve the exact least-privilege ownership/grant
   plan and the authority that applies it.
2. **Extension authority unresolved:** `pgcrypto` is required, but the
   responsible platform/migration authority and verification method are not
   yet approved.
3. **Safe staging probe absent:** no repository-owned tool currently reports
   content-free migration ledger, station, and role-boundary facts. The
   execution gate must approve an observation method or add one under separate
   local implementation authority.
4. **Recovery point mechanism unresolved:** backup format, integrity method,
   retention, protected storage, and restore target are deferred to M2.4; a
   minimum verified pre-change recovery point is still required before M2.2.
5. **Transport/version confirmation unresolved:** the owner must approve the
   staging PostgreSQL version/transport policy and demonstrate that it does not
   create public exposure. No connection attempt is authorized to determine it.
6. **Documentation consistency:** `README.md` still describes M1 as
   in-progress and lists local Compose/migration commands, while
   `docs/ARCHITECTURE.md` contains historical SQLite M0 wording. Those documents
   need a separately reviewed consistency update before an operator runbook is
   relied upon.
7. **M2.4 objectives:** the proposed 24-hour RPO and four-hour RTO are planning
   targets, not accepted commitments; the owner must accept or revise them.
