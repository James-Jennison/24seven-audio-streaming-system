# M3.2 Additive PostgreSQL Persistence and Migration Design

## Status, purpose, and non-authority

**Status: local documentation/design record; non-operational.** M3.2 defines
the future additive PostgreSQL persistence design that realizes the M3.1
station-scoped asset-lifecycle contract. It does not create, revise, execute,
or approve a migration; grant a role; connect to a database; activate a worker;
or initiate media, provider, runtime, encoder, Icecast, listener, deployment,
or production activity.

This is the authoritative design handoff for [M3.2 in the roadmap](ROADMAP.md#M32--additive-postgresql-persistence-and-migration-design). It is
limited to the Programming Control Plane and does not authorize M3.3 or any
later work. A separate explicit owner approval is required for the next bounded
sub-milestone.

## Starting evidence and conventions

M3.1 defines asset state, station isolation, immutable provenance, idempotency,
content-free evidence, and four-plane separation. The accepted M2 baseline
established PostgreSQL as the sole live persistence target, an ordered
`schema_migrations` ledger, transactional migration application/ledger record,
separate runtime and migrator connection references, and separately approved
least-privilege, backup, restore, and evidence-review boundaries.

`b73ed48` already contains an unrun `003_m3_asset_lifecycle.sql` candidate and
associated local-only contracts. This M3.2 record reviews that candidate as
evidence only; it does not treat it as accepted M3.2 implementation, alter its
contents, or authorize its execution. The existing runner records migration
filenames/order in the ledger; it does not currently add a migration-content
checksum column. M2 backup/recovery artifacts use content-free SHA-256
integrity evidence. M3.2 therefore requires an approved future migration run to
identify the reviewed Git commit, ordered filename, and externally verified
artifact digest in content-free evidence, without retrofitting or bypassing the
existing ledger convention.

## Persistence principles

- PostgreSQL is the sole future live store. No SQLite, SAM, PAL, SHOUTcast, or
  legacy runtime dependency is part of this design.
- All M3 rows, references, predicates, updates, and foreign references require
  both `id` and `station_id`. A cross-station relationship fails as
  `station_reference_forbidden`; missing or out-of-scope resources fail as
  `not_found` without ownership disclosure.
- Source references, provenance references, idempotency keys, and candidate
  references are opaque handles. No future persistence field is a media path,
  filename, URL, binary payload, credential, token, CSRF value, provider
  payload, or raw error.
- A persistence operation records control-plane state only. It has no direct
  adapter or command path to file processing, schedule publication/execution,
  playout, source encoding, relays, Icecast mounts, or listeners.

## Future additive record families

The following are logical record families, not permission to add tables now.
All names are descriptive design labels; final physical names and columns need
their own reviewed migration artifact under a later approved goal.

| Record family                                   | Station-scoped relationship and minimum future purpose                                                                        | Immutability / uniqueness expectation                                                                             |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Intake proposal/request                         | `id + station_id`; one opaque source reference and station-local idempotency key.                                             | `UNIQUE (station_id, idempotency_key)`; duplicate returns the original request/job outcome without starting work. |
| Intake job                                      | `id + station_id`; references its request using a same-station composite relationship.                                        | One job lineage per request/attempt policy; state/timing changes use constrained transitions.                     |
| Asset record                                    | `id + station_id`; durable asset lineage separate from request and schedule.                                                  | Identity is never reassigned across stations; lifecycle eligibility is controlled, not a media location.          |
| Asset revision / provenance                     | `id + station_id`; references its asset with the same station; carries opaque source/provenance and safe integrity reference. | Append-only; `UNIQUE (asset_id, station_id, revision_number)`; no update/delete of approved provenance.           |
| Processing / analysis result                    | `id + station_id`; references one asset revision in the same station.                                                         | Append-only measured facts and derived recommendations, versioned by analysis contract; no applied DSP setting.   |
| Metadata candidate                              | `id + station_id`; references one revision in the same station with opaque provider/candidate provenance and confidence.      | Append-only candidate; automatic overwrite of an approved revision is forbidden.                                  |
| Metadata resolution                             | `id + station_id`; references a candidate in the same station and an authorized decision actor.                               | Append-only approve/reject decision; one active resolution policy is explicit and deterministic.                  |
| Lifecycle failure / quarantine / retry evidence | `id + station_id`; references the request/job/revision it concerns in the same station.                                       | Append-only safe category, retry eligibility, safe UTC timing, and opaque IDs; no raw exception or media detail.  |

Every referenced family must expose `UNIQUE (id, station_id)` or an equivalent
candidate key before it can be the target of a composite foreign key. A simple
foreign key on `id` alone is insufficient for M3 ownership validation.

## State, idempotency, and transition constraints

The future schema must constrain the M3.1 lifecycle:

`proposed → validated → approved_for_processing → processing → analyzed → metadata_pending → ready_for_schedule_use`

with terminal/recovery branches `rejected`, `quarantined`, `failed`, and
`superseded`. Only the following recovery edges are eligible: `failed →
validated` and `quarantined → validated`, each as an explicit authorized retry.

Future persistence must use both declarative state-domain checks and an
atomic transition guard (for example, a reviewed transition relation plus a
transactional procedure/trigger). A caller must provide expected current state
and `id + station_id`; a stale or illegal transition makes no change and yields
a safe validation/not-found result as appropriate. The guard must not emit raw
SQL, source, or content in its error path.

Idempotency is deterministic and station-local:

- First creation reserves the opaque idempotency key and records one request.
- Repetition of that key for the same station returns the original opaque
  request/job identity and must not create a duplicate job, revision, analysis,
  or audit event that implies a second processing attempt.
- A matching key in a different station is unrelated and remains inaccessible
  through the first station.
- A retry is not an idempotency collision: it is an explicit new authorized
  attempt linked to retained, content-free prior failure evidence.

## Immutability, retention, and recovery design

Future migrations must enforce append-only revisions, provenance, results,
candidates, resolutions, and failure evidence through least-privilege grants
and a database-level mutation guard. Corrections create a later immutable
record; `superseded` changes future eligibility without erasing history.

M3.2 creates no retention schedule. Until a separately approved retention and
privacy decision exists, immutable provenance and safe evidence are retained
according to the existing database backup/recovery controls; no automatic
pruning, cascade deletion, or content-bearing archival is permitted. Any future
retention process must preserve referential integrity, station isolation,
recoverability, and content-free evidence.

The future migration must be additive and transactionally recorded in the
existing ledger. A failed migration rolls back its transaction; the ledger
record is written only with the successful transaction. There is no automatic
down-migration. A post-approval defect stops the run and is addressed by either
an owner-approved forward-fix or the separately approved M2 recovery process.
No M3 migration may change accepted M1/M2 rows, grants, backup policy, or
runtime behavior without an independently reviewed scope.

## Index and query design expectations

The future physical migration must document each index against a station-scoped
query. The minimum design set is:

- `station_id` plus request creation/order and lifecycle state for operator
  status and safe work-queue visibility;
- `station_id + idempotency_key` as the unique duplicate-prevention key;
- composite parent/child station-reference keys for joins and foreign-key
  validation;
- asset/revision sequence and lifecycle eligibility indexes for later M4
  catalog evaluation, not schedule publication;
- revision/analysis-version and candidate/resolution indexes only where they
  preserve append-only deterministic lookup; and
- `station_id` plus safe occurred-at ordering for audit/failure evidence.

Index design must not expose raw source values in explain output or create a
global ownership lookup. Capacity planning, query plans, partitioning, and any
retention index are deferred until separately approved evidence exists.

## Least-privilege authority separation

The following future authority classes extend the accepted M2 separation model.
They are design boundaries, not role creation or grant instructions.

| Authority class                    | Future M3 persistence responsibility                                                                                                  | Explicitly excluded                                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner / decision authority         | Approves a bounded change, acceptance, rollback/forward-fix decision, and risk disposition.                                           | Routine DDL/DML, runtime, worker, backup/restore, or listener operation.                                                                          |
| Migration authority                | Applies only the reviewed additive migration and ledger record during a separately approved run.                                      | Long-lived application use, runtime/worker operation, backup/restore, role administration outside approved setup.                                 |
| Control-plane runtime authority    | Performs only approved station-scoped M3 DML and content-free audit writes after a future activation approval.                        | DDL, extension/role/ledger control, cross-station access, worker dispatch, scheduling/runtime/encoder/Icecast control.                            |
| Future processing-worker authority | Under a later M3.4 approval, reads only approved same-station job/revision references and appends bounded results/failure categories. | Schema/ledger/role control, arbitrary source access, schedule/runtime/encoder/Icecast action, network/provider access unless separately approved. |
| Runtime authority                  | Future M5 read-only consumption of approved M4 Published artifacts, never an M3 writer.                                               | M3 intake/revision/metadata mutation, schema control, or asset-readiness execution.                                                               |
| Backup authority                   | Creates/verifies only separately approved recovery artifacts under the M2 backup boundary.                                            | Application DML, migration, restore, role management, or M3 operational activation.                                                               |
| Restore authority                  | Restores only to a separately approved isolated recovery target.                                                                      | Active staging/production writes, ordinary backup, migration, or runtime authority.                                                               |
| Evidence-review authority          | Reviews content-free pass/fail references and decision records.                                                                       | Database content, raw grants/SQL, secrets, media, or operational control.                                                                         |

Future grants must be additive, table-specific, reviewed with the migration,
and revoked/disabled outside their approved window where the M2 model requires
it. No shared privileged identity, superuser fallback, or alternate credential
may bridge these boundaries.

## Content-free audit and evidence requirements

M3 persistence audit/evidence may contain only action type, station ID, opaque
entity ID, safe state/category, safe UTC timing, safe count, reviewed artifact
identity, authority class, and pass/fail outcome. It must never contain media
contents, title/artist metadata, filenames, paths, tags, binary data,
credentials, tokens, CSRF values, provider responses, raw SQL, database rows,
or unbounded exception text.

The database audit mechanism must not make M3 state transitions depend on
content-bearing log construction. An audit/evidence failure that cannot be
reported safely stops the bounded operation and is classified only by a safe
category for owner review.

## Four-plane non-dispatch boundary

M3.2 persistence belongs only to the Programming Control Plane. It may store
an authorized future intent but cannot initiate processing, alter an M4 schedule
state, execute an M5 runtime artifact, change a Source Encoder Layer profile,
operate a relay or Icecast mount, or affect listeners. The Playout & Automation
Runtime, Source Encoder Layer, and Listener-Facing Icecast Layer remain
separately deployable and require their own later approvals.

## Future migration and staging evidence gate

Before any future M3 schema implementation or staging rehearsal, a new explicit
owner authorization must name the reviewed commit, ordered migration filename,
artifact digest, target classification, migration authority, required grant
artifact, recovery-point decision, transaction/ledger stop path, validation
probes, rollback/forward-fix owner, and content-free evidence boundary.

Required evidence includes additive-schema review; migration-order/ledger and
artifact-integrity confirmation; authority separation; no SQLite; station
isolation including composite references; immutable/idempotent/transition
validation; backup/recovery compatibility; inactive Runtime/Encoder/Icecast
planes; and final safe cleanup or inactive state. This design record creates no
standing authorization for such a run.

## M3.2 acceptance and next human gate

M3.2 acceptance requires review of this design against M3.1, the accepted M2
migration/role/recovery conventions, the existing unrun candidate, and the
authoritative roadmap. Acceptance is decision-only: it neither applies nor
accepts a migration or runtime activation.

The next permissible work is separately approved **M3.3 — safe
source-reference, quarantine, and rejection model** planning. M3.3 must not
resolve a source reference, access media, or activate a worker. Any ambiguity
in ownership, immutability, authority separation, recovery behavior, or
content-free evidence stops the sequence for an owner-approved correction or
deferral.
