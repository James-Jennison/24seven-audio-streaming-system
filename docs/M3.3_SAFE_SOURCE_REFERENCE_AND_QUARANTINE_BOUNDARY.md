# M3.3 Safe Source Reference and Quarantine Boundary

## Status, scope, and non-authority

**Status: local-only implementation; non-operational.** M3.3 completes the
Programming Control Plane boundary for opaque, station-scoped source-reference
validation, quarantine/rejection classification, and explicit retry
eligibility. It implements no source intake, storage access, migration, worker,
parser, media analysis, provider request, schedule publication/execution,
playout, encoder, relay, Icecast, listener, deployment, or production action.

This record is the authoritative completion record for [M3.3 in the
roadmap](ROADMAP.md#m33--safe-source-reference-quarantine-and-rejection-model).
It follows the M3.1 lifecycle contract and M3.2 persistence design. Completion
does not authorize M3.4 or any later item.

## Implemented control-plane boundary

The local domain now separates a source-reference record from an intake request.
Each `StationScopedSourceReference`, validation outcome, quarantine record, and
rejection record has its own opaque `id` and `station_id`. Every relationship
uses both values:

- an internal mismatched station relationship fails as
  `station_reference_forbidden`;
- public reads scoped to the requesting station return `not_found` for a
  missing or out-of-scope record, without ownership disclosure; and
- retries, request reads, job reads, failure checks, and lifecycle updates use
  the selected station in their query/predicate or fixture key.

Only the two pre-existing source classes are accepted:
`operator_staged_reference` and `managed_source_reference`. Their values are
opaque handles with a bounded safe-character form. A slash, traversal marker,
or malformed handle is rejected. The boundary has no path resolver, URL client,
file handle, binary buffer, media tag parser, or filesystem capability.

## Safe validation, quarantine, and rejection records

Validation produces a deterministic, append-only,
`SourceReferenceValidationOutcome`. It contains only opaque IDs, station ID,
bounded state/category, recovery eligibility, and UTC timing. Its categories
are `accepted`, `invalid_opaque_reference`, `unsupported_source_kind`,
`ownership_unverified`, `policy_rejected`, and `limit_exceeded`; none carries
source content or an unbounded error string.

The fixture-only `DeterministicSourceReferenceBoundary` is intentionally
in-memory and receives only safe test records. It has no adapter dependency and
cannot access a filesystem, process, network, provider, runtime, encoder,
relay, or Icecast service. Duplicate validation for the same station and intake
request returns the same immutable outcome. A conflicting source reference for
that idempotency identity is rejected without disclosing either reference.

`QuarantineRecord` and `RejectionRecord` are strongly typed views of those
append-only outcomes:

- a quarantine records a bounded category and
  `requires_explicit_authorized_retry`;
- a rejection is terminal and is `not_eligible` for retry; a corrective action
  requires a new station-scoped proposal rather than overwriting history; and
- an outcome object is immutable locally. Future PostgreSQL persistence must
  retain M3.2's append-only provenance/outcome design; M3.3 neither revises nor
  applies its unrun migration candidate.

No outcome changes an approved asset revision. Remediation can only append a
safe outcome or a future revision/provenance record under a separately approved
persistence action.

## Lifecycle and explicit recovery rule

M3.3 preserves the M3.1 lifecycle exactly. A source-reference validation can
support the existing `proposed → validated` or `proposed → rejected` control
plane transitions. Quarantine remains a bounded branch only from
`processing`, `analyzed`, or `metadata_pending`; M3.3 does not enter those
states or start processing.

The only recovery transition is `quarantined → validated` or
`failed → validated`, and only when retained safe evidence marks it eligible.
The operator must explicitly invoke the CSRF-protected, station-authorized
retry control. The deterministic boundary appends a separate immutable recovery
authorization record, while the repository path records the state transition
and a content-free audit event; neither resolves a source, enqueues work, or
dispatches a worker.
Rejected items have no recovery endpoint. `ready_for_schedule_use` remains
asset eligibility only, not M4 publication, M5 execution, M7 encoding, or
listener availability.

## Operator/API visibility and authorization

The existing station-scoped M3 API/UI now makes quarantined and failed records
eligible for an explicit **Authorize eligible retry (no processing)** control.
Rejected records show an accessible terminal status instead. The API requires
the established session, station authorization, programming authority, and
CSRF validation. A retry outside station scope reports `not_found`; an explicit
cross-station internal relationship reports `station_reference_forbidden`.

The dry-run endpoint remains read-only: it validates only bounded opaque request
shape, returns `processing: disabled`, and invokes neither persistence nor the
source-reference fixture boundary. It does not accept an upload or inspect a
source reference. No route exposes an action for a worker, subprocess, parser,
schedule, runtime, encoder, relay, mount, or listener service.

## Audit and plane separation

M3.3 audit/evidence uses only action type, station ID, opaque entity ID, safe
state/category, timing, and safe count information. It never includes media
contents, titles, artists, filenames, paths, tags, binary data, credentials,
tokens, CSRF values, provider payloads, or raw SQL. Tests assert this boundary
for validation outcomes and repository audit values.

The work belongs exclusively to the Programming Control Plane. It cannot cause
an action in the Playout & Automation Runtime, Source Encoder Layer, or
Listener-Facing Icecast Layer. PostgreSQL remains the sole future live store;
no SQLite or SAM, PAL, SHOUTcast, or other legacy dependency was added.

## Evidence and next gate

Local tests cover opaque-reference validation, safe out-of-scope behavior,
`station_reference_forbidden`, deterministic duplicate/conflict handling,
valid/quarantined/rejected outcomes, terminal rejection, explicit recovery,
immutable outcomes, content-free audit values, CSRF-protected retry, and the
absence of processing/runtime/encoder/relay/Icecast dispatch paths.

No migration was created or executed. No database connection, container,
worker, subprocess, FFmpeg, parser, real-media action, provider call,
runtime/encoder/Icecast contact, deployment, or production action occurred.

The next permissible item is a separately approved **M3.4 — Asynchronous
processing-worker boundary**. That approval must not be inferred from M3.3 and
must keep its future worker disabled by default, bounded to approved job IDs,
and unable to access the filesystem, network, process, schedule, runtime,
encoder, relay, or listener-facing planes without later explicit authority.
